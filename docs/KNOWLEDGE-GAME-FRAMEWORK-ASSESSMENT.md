# 从挖矿 MVP 到开放知识游戏框架：代码评估

2026-10-16。本次是代码审查、针对性测试与目标架构建议，**不是新框架已经实现的声明**。未修改游戏运行时代码、未迁移引擎、未发布新版本。

## 1. 产品定位

目标不是把一次性的知识视频简单改成“看完答题”，而是让知识成为可操作、可复习、可更新、可分叉的世界：

> 创作者或编码 Agent 编写知识游戏 → 玩家游玩并留下学习证据 → 对话帮助理解 → 内容继续更新 → 其他人复制、修改、发布衍生世界。

StudentBuddy 是参考宿主和学习伙伴；泰拉瑞亚式挖矿是第一个玩法模板，而不是以后所有内容必须遵守的唯一玩法。平台的长期价值应当是开放协议、稳定运行时、创作工具链和可复用作品，不是绑定某个模型或短视频热度。

本次查看了主仓库 shared/server/web、open-engine 内核，以及相邻独立 MVP 的内容注册、地图、学习、存档、表现、搭子和房间实现。没有读取用户私密对话、密钥或线上数据库。

## 2. 当前代码的真实位置

**结论：已有可用的单机玩法验证、声明式扩展接口和部分引擎底座；尚不是可让第三方独立开发新玩法的通用知识游戏框架。可演进，不必推倒；但不能只继续往现有页面加接口。**

| 维度 | 已有实现 | 对长期目标的缺口 |
|---|---|---|
| 主体模块化 | shared/server/web 分离，服务端已有模型网关、学习事件、会话和插件层；行数、类型、测试登记门禁 | 独立游戏尚未接入真实对话与学习事件；不能把复用判分函数说成数据互通 |
| 内容注册 | 内容包命名空间、严格字段校验、容量上限、批量注册失败不改原状态；形象/NPC/能力可导入导出 | 尚无通用方块、独立物品、动画、音频、配方、任务/事件/交互组件注册体系 |
| 物品与行为 | 物品格和魔法统一；效果通过领域命令执行 | 效果枚举只有 teleport.spawn / light.place；创作者不能只写模块就增加新机制 |
| 地图 | classic/strata/RLE、编辑操作、分区、NPC 锚点、校验/预览、导出、多世界 | 固定 200×150×24；方块表、碰撞与生成依赖常量。不是通用关卡/分块世界系统 |
| 学习闭环 | 真正复用主体词条出题、判分和作答累计；发现时保存题目快照 | 仍是“挖掘→抽词条→选择/判断/填空”；暂无交互任务、实验状态、过程证据、rubric 和内容更新后的目标映射 |
| 事件 | 游戏发出带序号的事件，公开 API 可订阅 | 观察通知不是可编排的玩法运行时；最近 80 条事件也不是可持久回放日志 |
| AI 搭子 | 局部观察、受限意图/回复协议、共用物理、租约、序号与撤销 | 默认离线规则；未自动接主体模型。主程序本地 Agent 插件任务队列也还未适配游戏接口 |
| Agent 演进 | 配置提案、差异、用户确认、版本历史/回滚、能力 broker | 修改配置不等于修改程序；提示词/工作流未进入正式主体模型循环 |
| 联机 | 权威房间内核、适配器、双客户端 HTTP 测试、个人学习快照隔离 | 开发回环入口，无游戏内大厅、公网持久服务、客户端预测与升级协商 |
| 分享和二创 | 地图/包可导出，离线 HTML 和源码可携带 | 地图、依赖包、素材、知识来源没有统一作品封装；无依赖锁、作品谱系、版本迁移和一键 Fork/发布流程 |

- `packages/open-engine/package.json`：目前仅导出 agent/room/companion 三个内核，private=true；地图、内容注册、挖矿与渲染仍在独立 MVP，并非已完成的公共游戏 SDK。

- `packages/server/src/plugins/chat.ts`、`plugins/runtime.ts`：主体已有工具发现、调用、owner 隔离、确认、撤销等基础，不宜再造第二套模型或插件网关。
- `packages/server/src/learning/reply-practice.ts`、`routes/reply-practice.ts`：真实对话已能提炼来源于讲解的回忆练习，可成为双向适配入口，但原型尚未调用。

引用的独立 MVP 路径相对主仓库；该目录是单独工作成果，克隆主仓库不自动带上它。正式框架应把必要运行时、协议与参考内容纳入可获得的发布单元。

## 3. 优先补的不是“更多接口”，而是完整扩展闭环

公共接口宜少而稳定，扩展实现可以很多。建议按以下边界逐步拆分，**不是立刻创建一堆空包或微服务**：

```text
Studio / Player / 外部编码 Agent
         ↓ 同一套 SDK、Schema、校验与预览
World Project（可编辑源码） ───→ World Release（不可变可玩版本）
         ↓
内容运行时：注册表 + 事件/条件/动作 + 交互组件 + 有界调度
         ↓                         ↓
游戏模拟内核                     学习适配器
世界/实体/物理/命令               目标/题目快照/作答证据/复习
         ↓                         ↓
可替换表现适配器                  StudentBuddy 对话与学习服务
Canvas 首个实现                  共用现有模型网关/owner/持久化
         ↓
宿主：本地文件、存档、权限、包加载；联机时复用服务端权威规则
```

### A. 作品包与资产管线：先让一个世界成为独立项目

建议作品项目包括 manifest、地图、知识资料、内容定义、事件、脚本、素材、测试和 README。发布包包含可玩构建产物及源码获取信息，必要时同时带源码。不要只分发一个难以二改的打包 HTML。

manifest 应明确作品 id/版本、引擎兼容范围、入口、精确依赖锁与哈希、作者、代码许可、素材逐项许可、知识来源、父作品及其精确版本、迁移入口。包协议版本、引擎版本、内容版本、玩家存档版本要分开，不用一个 revision 兼任全部身份。

资产需要可引用的资源 id、atlas/动画/音频元数据和离线资源路径，不把所有美术限制在 32 行字符画。引入数量、尺寸、解码内存和每帧预算，超限给出可定位诊断，而不是简单取消所有容量限制。

**作品包与个人存档严格分离**：发布时不包含聊天、作答记录、API Key、配对令牌和账号信息。创作者测试用例可以随包发布，真实学习记录不随 Fork 传播。

### B. 行为扩展：必须能增加新机制，而不仅能换皮肤

提供实体/物品/方块/交互组件注册，以及稳定的事件、条件、动作契约，例如 interact、region.enter、item.used、learning.evidence.recorded。注册表必须同时服务模拟、渲染、保存和迁移，避免每种新对象都修改中心 switch。

保留三条创作路径：

1. **声明式内容**：JSON 地图、资产、规则图，适合多数 AI 生成内容，运行前可预览和诊断。
2. **SDK 行为模块**：编码 Agent 写 TS/JS，编译到隔离运行时，经宿主命令和事件交互；真正支持新的交互机制、模拟和 UI 组件，而非假装一组固定 JSON 就能覆盖所有游戏。
3. **完整源码 Fork**：用户要改物理、渲染、学习规则时可以改内核自行构建；官方兼容性认证与分享权限不是阻止其自由修改的门槛。

陌生作品不在主体页面直接 import/eval。脚本运行时需明确 CPU/内存/消息预算、超时终止、状态序列化与宿主能力范围。Worker 本身不是完整权限沙箱；其网络/存储能力也要隔离。服务器执行陌生脚本还需独立进程/容器等边界，不能把同进程函数调用包装成安全沙箱。

核心规则尽量由服务端/单机共用纯逻辑执行，随机源和时钟显式注入；视觉脚本不能替玩家制造“已掌握”事实。先做一种最小交互模块，不先引入庞大的通用 ECS 或多引擎维护负担。

### C. 学习是玩法的一部分，不是覆盖游戏的答题弹窗

第一版可以从词条题型继续玩，但框架还应容纳：接电路、调整参数、按因果排序、运行算法、操作实验等交互。必须描述学习目标、任务初态、可用操作、过程证据、评价规则、来源和版本。

例如“电路矿洞”：玩家把电路接通让矿车运行，任务根据连接/实验结果记录证据；对话读取玩家尝试过的方案给予提示。此时知识就是玩法因果，不是挖掉一个方块后换出一道相同形式的题。

`EncounterProvider / InteractionRuntime / EvidenceAdapter` 等是建议边界，名称不重要。重要的是新交互由模块注册，题目快照、来源、主观题待评状态和事件幂等由共同契约表达。

双向互通不等于复制全部聊天：游戏只上传用户选择共享的任务/尝试；对话输出可校验的内容提案，经确认影响后续世界/练习，不用模型回复直接覆盖地形或已完成证据。AI 不可用时，已发布内容仍能学习。

### D. 更新与 Fork：保护作品谱系，也保护学习进度

- 发布版本不可变；草稿可编辑，更新后产生新版本。内容哈希用于校验一致性，不等于作者可信认证。
- Fork 保存父作品精确版本及来源信息，获得自己的作品身份；依赖按锁文件解析，不默默跟随 latest。
- 角色/任务/学习目标采用稳定 id。更新先预检与备份，再做显式迁移；失败保留旧版本和旧存档。
- 已发现题目保留原始快照。知识被纠正时保留旧证据与新版本关联，不能悄悄改掉历史答案；不同 Fork 的“掌握”也不能只因名称相同就直接合并。
- 联机房间固定内容指纹；升级需停房迁移或有明确版本协商，不能让两个客户端各自热更脚本。
- 先支持完整项目复制和分叉；随后再做语义化差异/合并。地图、二进制资产和学习进度不是文本 Git merge 自动能解决的。

### E. 创作者工具链：外部 Agent 的第一入口

提供一致的 create → validate → preview → test → pack → publish 工具链、TS 类型、机器可读 Schema、可执行示例和可定位到文件/字段的诊断。CLI 是底座，UI 和 MCP 是同一宿主服务的入口，不是维护三套校验逻辑。

外部 Agent 应能在空目录创建作品、测试无头模拟、预览并交付可玩包，而不必知道主体内部路径、修改 app.mjs 或直接读数据库。公开兼容性测试比接口数量更有价值。

## 4. “像 GitHub”先复用 GitHub，不先重造它

建议先做**源码项目 + 可玩预览 + 本地导入导出 + Fork 谱系**。托管可用普通 Git 仓库和静态资源；需要账号/API 的发布是可选适配，不是离线使用的前提。

第二步再建立轻量世界目录，索引作品 manifest、封面、版本、依赖、源码链接和播放入口。目录可镜像、可自托管，不让唯一中心服务成为免费项目的生死点。Issue/PR、讨论、账号和大文件存储初期优先借用现成服务。

第三步才建设站内可视化二创、作品差异、审核/举报、兼容性标记和联机邀请。不承诺未经测试的作品“一点即永远兼容”，也不把“上传 ZIP”称为完整社区生态。

## 5. 免费与可修改的长期设计

现有主仓库和 MVP 使用 MIT。可维持“官方软件、协议、核心工具和本地玩法免费开放”，但需区分：

- 开源/免费分发不等于远端模型、托管、素材 CDN 和联机服务器没有成本。基本游玩不强制调用模型；支持用户选本地模型/自有接口，云生成可选。
- MIT 允许修改、再分发和商业使用，不保证衍生版本继续开源，也不禁止别人收费。若产品意图只是“我们官方不收费”，与 MIT 一致；若要强制所有二创免费/开源，则是另一项许可治理决策，不应在 README 口号中悄悄改变已有授权。
- 代码、素材、知识文本分别记录许可。第三方素材按其许可复用，不能因为是泰拉瑞亚模组、免费网页或公开 GitHub 项目就视为可重新分发。
- 通过离线可玩、内容缓存、按需 AI、静态发布、镜像/自托管和可替代托管降低持续成本；不要让核心学习每一步都依赖官方买单的生成调用。

依据：[MIT 正文](https://opensource.org/license/mit)、[Open Source Definition](https://opensource.org/osd)、[Kenney 资产许可说明](https://kenney.nl/support)。本评估不改变现有 LICENSE。

## 6. Godot 的位置

**先建立引擎无关的作品/学习/行为契约，近期保留当前浏览器模拟和已认可的手感；不因“需要扩展”立即重写 Godot。** 这是基于现有代码与交付形态的工程判断，不是断言 Godot 不适合。

Godot 的 TileMapLayer、资源系统和编辑器对复杂关卡与专业美术工作流有价值；但引入它不会自动得到学习证据、作品依赖锁、Fork 迁移或 AI 内容标准。Web 导出和网络能力也需要按目标平台实测。参考：[TileMaps](https://docs.godotengine.org/en/stable/tutorials/2d/using_tilemaps.html)、[Web export](https://docs.godotengine.org/en/stable/tutorials/export/exporting_for_web.html)。

当复杂动画/物理/关卡制作成为明确瓶颈，再拿同一个小型知识世界做 Godot 技术验证：对比启动包大小、移动浏览器性能、离线保存、文字清晰度、脚本隔离、学习桥接和联机适配成本。验证通过才决定引擎承担哪些职责，不承诺两套模拟天然一致。

## 7. 建议执行顺序与验收

| 阶段 | 重点交付 | 不能被文档代替的验收 |
|---|---|---|
| P0：整理边界 | 保留 physics/手感；抽离内容与学习适配；统一作品包 v1 与基础 SDK/CLI；纳入主仓库可发布构建 | 第三方在空目录创建、验证、打包一个世界；主程序无源码修改即可导入游玩 |
| P1：证明真扩展 | 事件/条件/动作与首个交互模块；真实对话/学习桥接；资源引用与保存/迁移契约 | 两个独立项目：挖矿知识世界 + 电路或算法实验世界。第二个必须有新机制，不是换题库和贴图 |
| P2：分享与二创 | 源码/可玩包、依赖锁、来源/许可、父版本、更新预检和可回退迁移；静态目录 | A 发布 → B 无 Key 游玩 → B Fork 改机制/素材 → C 能玩 B 版本；更新不会清掉 A/B 旧进度或泄漏个人数据 |
| P3：协作规模化 | SDK 行为模块隔离、兼容性套件、编辑器；再建设浏览器联机和持久房间 | 脚本死循环可终止；未知能力被拒；离线不失控；两客户端内容一致；断网和旧版本有明确恢复策略 |

每阶段补强对应边界，不等全部框架完工才让人创作。不要先用大量抽象包、微服务、通用脚本语言或自建 Git 平台消耗项目维护能力。

- 主体针对性测试：reply-practice 路由、plugin-ecosystem、agent-bridge、plugin runtime，**4 files / 38 tests passed**；临时测试数据隔离并清理。

## 总结

现有成果应该作为第一个参考游戏保留。下一次架构提升应以“**别人不改内核就能写出第二个不同玩法的知识游戏，并分享、Fork、更新它**”为目标，而不是以新增按钮、接口数量、改用某个引擎或新增特效为目标。
